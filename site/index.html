Szenario & Last einstellen

Fixe Architektur-Entscheidung dieses Labs: die Datenbank läuft immer On-Prem (dieser Docker-Postgres/Patroni-Stack). Der App-/Web-Layer gilt als Cloud- bzw. Multi-Cloud-gehostet — wähle unten Server-Größe, gleichzeitige Nutzer und Zielprovider; darunter erscheint der fertige Befehl.

App-Hosting (Cloud / Multi-Cloud)

Datenbank-Standort ist fest auf On-Prem verdrahtet — nur der App-Layer ist wählbar. Ohne Cloud-Auswahl läuft die App ebenfalls On-Prem (Baseline-Vergleich).

Das Server-Modell setzt echte Docker-CPU/RAM-Limits auf den DB-Containern und bleibt bis zum nächsten Testlauf aktiv. Komplett zurücksetzen: docker compose up -d --force-recreate postgres1 postgres2.

Startet new_experiment.py + run_failover.py direkt im Dashboard-Container (killt kontrolliert den aktuellen Primary) — Fortschritt erscheint oben im Live-Panel. Nur ein Lauf gleichzeitig möglich.

ECHTE DATEN
On-Prem / Cloud verbinden
Drei Wege, echte Messungen einzuspielen — Uploads und API-Pushes landen als MEASURED-Evidence in experiments/ und aktualisieren die Kennzahlen oben automatisch.

  

    

      
0 · Aus Azure oder OCI exportieren

      
Bevor sich etwas hochladen lässt, müssen die Rohmetriken erst aus der Cloud raus. Beide Provider liefern direkt verwendbares JSON:

      
Azure — Azure Monitor liefert Replication Lag, Verbindungen und Latenz pro Ressource:

      
az monitor metrics list \
  --resource <resource-id> \
  --metric "replica_lag,active_connections,connections_failed" \
  --start-time 2026-09-03T09:00:00Z --end-time 2026-09-03T09:10:00Z \
  --output json

      
OCI — der Monitoring-Service liefert dieselben Metriken über eine Query gegen den oci_database-Namespace:

      
oci monitoring metric-data summarize-metrics-data \
  --compartment-id <compartment-ocid> \
  --namespace oci_database \
  --query-text 'ReplicationLag[1m].mean()' \
  --output json

      
Beide CLIs exportieren rohe Zeitreihen (Lag, Latenz, Fehler, Durchsatz) — für RTO/RPO braucht es zusätzlich einen echten, kontrollierten Failover-Test mit eigenen Zeitstempeln, analog zu scripts/run_failover.py. Die exportierten Werte anschließend in unser Schema (rto_seconds, replication_lag_seconds_max, workload.*) umrechnen und hochladen oder per API pushen — zwei Beispieldateien im Zielformat:

      

        azure-demo-result.json
        oci-demo-result.json

2 · API anbinden

      
Für automatisierte Pushes aus eigenem Monitoring/CI, ohne manuellen Upload:

      
curl -X POST http://localhost:8000/api/ingest \
  -H "Authorization: Bearer <DASHBOARD_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "experiment_id": "PROD-2026-09-03-01",
    "scenario": "primary-failure",
    "rto_seconds": 12.4,
    "acknowledged_write_loss": 0,
    "replication_lag_seconds_max": 0.8,
    "workload": {"p95_ms": 210, "p99_ms": 340, "error_rate": 0.01, "throughput_rps": 48.2}
  }'

      
Token steht in .env (DASHBOARD_API_TOKEN). Jedes Feld außer experiment_id ist optional.

CLOUD_ONLYCloud App + DB Primary
HYBRIDPrimary + synchronisierte Standby-Site


Bewusste Trennung in diesem Lab: DB On-Prem, App Cloud/Multi-Cloud
Datenhoheit und Compliance sprechen oft dafür, die Datenbank On-Prem zu belassen, während der zustandslose App-/Web-Layer flexibel auf einer oder mehreren Clouds skaliert. Dieses Setup emuliert genau das: die Postgres/Patroni-Knoten laufen fest lokal, die Demo-API steht stellvertretend für den frei platzierbaren App-Layer. Konfigurierbar im Abschnitt „Szenario & Last einstellen“.
